## 铁律：一个技术文档 = 一张图

图多了没人看，token 也白烧。多主题 → 拆成多份文档，每份各一张图；**不要在一份文档里堆图**。

```
docs/diagram/
├── design.md    唯一技术文档：1 张图 + 表格 + design_to_code YAML
└── assets/
    └── design.svg   与文档同名，由 design.md 内的图块渲染
```

其他图型（时序 / 状态 / ER）的写法在 `evals/samples/` 里按需取用，**不预先生成**。

## 分工原则

| 载体 | 负责 | 不负责 |
|------|------|--------|
| **图** | 拓扑、依赖、层次 —— 「30 秒看懂」（**人话**） | 类名、path:line、表字段、判据 |
| **§0 节点证据表** | `path:line`、日志 —— 「有据可查」 | 复述整张图 |
| **§关键数字 / §排查脉络** | **可选节**；有则填，无则删标题 | 编造数据、空壳占位 |
| **其它表格** | 清单、映射、判据 | 空间关系 |
| **YAML** | 机器消费的交接契约 | 给人看 |

**关键**：说明只写**图上没有的**。图能表达的一律不写字。

## 图的第一眼要求

新人 30 秒要能回答三个问题：

1. **这是什么**（一句话）
2. **有哪些核心模块**（≤7 个，多了就拆）
3. **谁依赖谁 / 数据怎么流**

达不到就重画，不是加文字补。

**交付前跑一次 `node scripts/render.mjs docs/diagram/ --strict`** —— 构图审计（画布宽/宽高比/节点数/边数/填充率）不过就是白画，先把信息砍进表（细则 `layout.md`）。

## 反模式

| ❌ | ✅ |
|----|----|
| 图节点写 `FooService.java:88` | 图写「处理订单」；证据进 §0 |
| 图边写 `sendLiveCoupon` | 图边写「发券」；方法名进 §0 |
| 一份文档塞 5 张图 | 一份文档 1 张图 |
| 只有文字没有图 | 一图 + 表格补细节 |
| 图 + 大段复述图的文字 | 图 + 只写图外信息 |
| 一张巨型图塞完所有 | 一图一主题；**超 12 节点 / 14 边 / 画布 1200px 就砍进表**（`layout.md`） |
| 把 §关键数字/§排查脉络/§解决方案 的内容再画进图 | 图只画主链 + 锚点；明细留在那三张表里 |
| 为「风险」「决策」单独出图 | 风险/决策是清单 → 用表格 |
| 图与代码不符且不标注 | 不符处标 `⚠️ 与代码不一致` |
| 手工编辑 `assets/*.svg` | 只改 md 里的图块，重跑渲染 |
| 每张图都塞时间轴/怀疑点 | D0 勾选才用；架构图通常不需要 |
| 没监控数也写「约 300」 | 无数不写；改 UNKNOWN 或删 |
| 空着 §关键数字 占位 | 不用就删整节 |
