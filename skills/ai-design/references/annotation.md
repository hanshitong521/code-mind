# annotation · 按需加注（通用，非事故专用）

**原则：D0 先判读者要懂什么，再选加注维度。** 没有「每张图都必须有数字 / 怀疑点 / 时间轴」——有则写，无则删，不凑字段。

## D0 出口（画前先写 3 行，不进图）

```
读者三问：〔这是什么 / 核心模块 / 关系或结论〕
输入类型：〔架构 / 流程 / 事故排查 / 数据模型 / 混合〕
选用标注：〔从下方菜单勾选，可空〕
```

**选用标注**从菜单勾选 0~N 项；一项都不勾 = 只画拓扑 + 人话，完全合法。

## 标注菜单（按需勾选，禁止全塞）

| 维度 | 何时**用** | 何时**跳过** | 图上怎么写 | 表上怎么写 |
|------|-----------|-------------|-----------|-----------|
| **关键数字** | 输入有**可验证**度量（监控、日志计数、用户给的数） | 纯架构、需求草案、无数可依 | 副标题 **最多 1～2 个**最关键数（规模/阈值） | 完整序列、明细、来源 → **§关键数字**（有则建，无则删整节） |
| **时间锚点** | 问题涉及时序、窗口、先后 | 无时序关系 | 节点/边标 **一个**时间点或时段 | 分钟级/事件链 → §关键数字 或 §脉络 |
| **排查态** | 多假设需区分已证/未证 | 设计新功能、单一路径无争议 | `classDef` 语义色（见 `mermaid.md`） | §排查脉络：确定 / 怀疑 / 否定 / 未知 |
| **症状 vs 根因** | 故障、性能、体验类 | 绿field 设计 | 症状 1 节点；根因加粗/暖色 | 脉络表里写判定依据 |
| **瓶颈** | 已定位拥塞点 | 无性能议题 | 标「打满」「慢」+ **若有数**写 1 个 | 完整指标进表 |
| **UNKNOWN** | 缺证据且影响理解 | 已全部证实 | 虚线节点 `待确认：…` | §未知 / 待确认 |
| **业务流程链** | 几乎任何图（**硬要求**） | 纯静态架构无步骤 | subgraph「怎么跑」逐步箭头 | 不在表复述全流程 |
| **对策概要** | 问题已定位且有方案/建议 | 纯理解、无改法 | **默认不进图**；要进就 ≤3 条虚线绿框，**挂在对应瓶颈旁**，不另开 subgraph 堆清单 | §解决方案：问题·现状·对策·预期（实现写 MD/YAML） |

## 事故/问题类 · 推荐图层（可组合，流程层不可省）

```
现象 →〔可选：时间/数字〕→ 业务流程（逐步）→ 瓶颈点 →〔可选：已否定假设〕→ 对策概要
```

**反例**：只画「已否定 / 确定根因」四个框，没有「触发→扫表→判规则→发券→等待」——读者看不懂怎么回事。

## 图 vs 表分工（防硬编码）

| 载体 | 规则 |
|------|------|
| **图** | 人话 + **读者 30 秒最该记住的 1～2 个事实**（可以是数、可以是态、可以都没有） |
| **§0 节点证据** | 有代码/日志锚点时**必填**；纯需求图可改为「需求原文」列 |
| **§解决方案** | 问题↔对策↔预期量级（**待验证**须标注）；实现逻辑不堆在图里 |
| **可选节** | §关键数字、§排查脉络… — **无内容就删标题** |
| **YAML** | 行为契约；禁过期 path:line（同 `design-delivery.md`） |

## 排查脉络表（仅当 D0 勾了「排查态」）

```markdown
## 排查脉络

| 态 | 项（人话） | 关键依据 | 图上对应 |
|----|-----------|---------|---------|
| 确定 | … | 日志/代码/复现 | 节点名 |
| 怀疑 | … | 待验证 | 节点名 |
| 否定 | … | 反证 | 节点名 |
| 未知 | … | 需要查什么 | UNKNOWN 节点 |
```

**无排查过程**（例如画公海列表架构）→ 整节删除，不要硬造「怀疑点」。

## 关键数字表（仅当 D0 勾了「关键数字」或「时间锚点」）

```markdown
## 关键数字

| 指标 | 值 | 时段/条件 | 来源 |
|------|-----|----------|------|
| … | … | … | 日志 / 监控 / 用户口述 |
```

行数按实际输入；**禁止编造**；用户没给、日志没查到 → 不进图也不进表，改 UNKNOWN。

## 双行标签公式（通用）

```
〔角色/动作〕<br/>〔副标题：可选的一个数 / 态 / 短结论〕
```

示例（同一公式，不同场景）：

| 场景 | 标题行 | 副标题行（按需，可省略） |
|------|--------|------------------------|
| 架构 | 订单服务 | 写入口唯一 |
| 流程 | 用户提交 | — |
| 事故 | 定时补券任务 | 触发 1 次 |
| 事故+有监控 | 发券调用 | 峰值 322 次/分钟 |
| 无数据 | 支付网关 | — |

## 反模式

| ❌ | ✅ |
|----|----|
| 每张图都画时间轴 subgraph | 只有涉及时序才画 |
| 没数据也写「约 300 次」 | 无数 → 不写或标 UNKNOWN |
| 架构图硬塞「怀疑 Python 挂死」 | 无排查语境就不写排查态 |
| 数字全堆节点上 | 图 1～2 个，余下进 §关键数字 |
| 空着 §排查脉络 占位 | 不用就删节 |
| 为画排查删掉业务流程 | 流程 subgraph 保留；排查叠在旁边 |
| 把三张表内容再画进图（节点冲到 20+） | 图只画主链 + 锚点，明细留表；预算见 `layout.md` |
| 对策写实现代码 | 图/表只写概要；代码进 §0 或 YAML |

## 解决方案表（仅当有问题点且已有对策建议时）

```markdown
## 解决方案

| 问题（图上节点） | 现状（有据） | 对策概要 | 预期效果（量级，待验证） | 优先级 |
|----------------|-------------|---------|------------------------|--------|
| 发券洪峰 | 峰值 322 次/分钟 | 队列 + 每分钟上限 | 峰值 ≤ 配置值（如 20~50/min） | P0 |
```

**预期效果**：可写「100 次 → 20 次」类量级，须标 **待验证/待排期**；无依据不编精确百分比。

## 与 D1 节点表的关系

D1 节点表增加可选列 **「加注」**：勾选的维度（数字/态/时间/无）。  
生成 DSL 时只渲染勾选项，**不默认填充**。
